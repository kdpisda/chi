## Material: the noisy pack never reaches the guard it was written for

`problems/noisy_bench` existed but had never been run (flagged for this in the
09-18 notes). Ran it this run through the scripted adapter, config in the
scratchpad, `--runs-root` off the repo. Nothing in the repo was modified to do
it: the pack's `solve(xs) -> prefix sums` contract is the same as
`optimize_function`'s, so `examples/demo_candidates.json` replays against it
unchanged.

```
run_id noisy-demo-4e2b63   iterations 3   total_cost_usd 0   status done
baseline  301 ops  scored 305.1409092126975   sha256:95b1df80
iter 0    301 ops  scored 314.0752743264603   sha256:650927fe
iter 1    904 ops  scored 933.1414112224109   sha256:410b8023
iter 2      1 op   scored   1.0772676031052   sha256:3b005691
every ITERATION_COMPLETE: evals_run 1
```

Two findings, both verified against the tree:

1. **The guard never fires on `chi run`.** `NoiseGuard` is constructed only in
   `chi/session/director_runner.py:76,79` (`build_noise_guard`), reached only
   through `chi/session/engine.py:543` (`DirectorHandle`), i.e. `/director` in
   the interactive session. `chi run` (`chi/cli.py:377`) goes to
   `chi/orchestrator/loop.py`, which picks the champion with
   `ledger.champion()` — `ORDER BY score_value ASC LIMIT 1`
   (`chi/store/ledger.py:58-66`). No re-benchmark anywhere on that path, which
   the event log confirms: `evals_run 1` on all three iterations, no extra
   `RESULT` rows. The pack's own docstring says it exercises "the Director's
   median-of-N NoiseGuard", so the pack is not wrong — but the shipped
   non-interactive entry point cannot exercise it, and that is what the post
   says.
2. **Not posted, but worth recording:** `bench.py`'s docstring claims "an O(n)
   rewrite really scores lower than the O(n^2) baseline". False for the explicit
   O(n) loop. The metric counts Python line events, so the loop pays 3 lines per
   element (904 ops) while the O(n^2) comprehension pays 1 and lets C-level
   `sum()` do the work (301 ops). Only `itertools.accumulate` (1 op) wins. The
   proxy metric ranks by interpreter lines, not by complexity class. That is a
   separate post and probably a docstring fix.

Fact check on every claim in E:
- "deliberately noisy problem pack": `problems/noisy_bench/problem.yaml`
  description, "a deliberately NOISY benchmark"; `repeats: 1` is set there on
  purpose.
- "chi's median-of-3 re-benchmark": `NoiseGuard` defaults to `n=3`
  (`chi/eval/noise.py:28`) and both construction sites pass `n=3` explicitly.
  The median test is `noise.py:44-48`.
- "The guard never fired": `evals_run 1` per iteration, above. No NoiseGuard
  import or call anywhere under `chi/orchestrator/`.
- "It only runs under the director": the two construction sites and the single
  `DirectorHandle` call site, above. There is no `chi` subcommand that starts a
  director; bare `chi` opens the TUI (`chi/cli.py:19-35`).
- "chi run just takes the best score": `ledger.champion()`, above. True
  regardless of `repeats`; with `repeats: 1` each stored score is also a single
  sample.
- "Same function, two comment variants, 301 ops each: 305 and 314": the pack's
  `candidate.py` and `demo_candidates.json[0]` are both
  `[sum(xs[: i + 1]) for i in range(len(xs))]` with different comments, so
  different `code_hash`, same 301 base line events (recomputed directly, not
  read off the run). Scores 305.14 and 314.08 are the two `RESULT` payloads.
  The spread is 2.9% and comes only from `_noise_factor(source, run_index)`.
- Not claimed: that this is a bug rather than a design split. The post says
  where the guard runs and what `chi run` does instead, both of which are facts.
