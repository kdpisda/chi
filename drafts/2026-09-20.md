## Material, verified this run

`problems/noisy_bench/bench.py` docstring: "an O(n) rewrite really scores lower
than the O(n^2) baseline". That is false, and the pack's metric is the reason.
Measured with the pack's own `_count_line_events` on its own input (seed 5, 300
floats), nothing in the repo modified, scratchpad script only:

```
O(n^2) comprehension        line_events= 301   wall median 545us
O(n) loop, 2 body lines     line_events= 904   wall median  23us
O(n) loop, body on one line line_events= 604   wall median  22us
itertools.accumulate        line_events=   1   wall median  15us
```

- All four return prefix sums agreeing with the baseline to 1e-6.
- The two loop variants compile to the same 22 bytecode instructions
  (`dis.get_instructions` opname lists compare equal). Only the source line
  layout differs, and the score moves 904 to 604. The metric prices formatting.
- `_count_line_events` counts `line` trace events, so the explicit loop pays per
  element while the comprehension pays once and lets C-level `sum()` do the
  quadratic work out of the tracer's sight.
- Wall clock is noisy at this size. Over 15 repeats of 200 calls each:
  quad min 439us / median 545us / max 820us, loop min 9.6us / median 23us /
  max 45us. Median over median is 24x, min over min is 46x, and the worst
  possible pairing is 9.9x. The post says 20x, which sits under all three. "10x"
  would have been the natural phrasing and is a banned string anyway.
- Not claimed in the post: that the pack is broken. It does exercise noise
  exactly as designed. The claim is narrower and true: the base cost it scores
  is interpreter lines, so it ranks a slower program first.

This also revises the 09-19 note, which recorded the O(n) loop at 904 ops and
`accumulate` at 1. Both numbers hold for the exact formatting used there; what
was missed is that 904 is a property of the layout, not of the algorithm. That
is the finding that makes the post.

## Follow-up for the user, not for this routine

`problems/noisy_bench/bench.py`'s module docstring should be corrected, and
possibly the metric with it. This routine only touches `posts.jsonl`,
`angles.md` and `drafts/`, so no code was changed. Two honest options:

1. Fix the docstring to say the base cost is executed Python line events, a
   proxy that favours C-level work and is sensitive to source layout.
2. Change `_count_line_events` to count bytecode instructions (`opcode` events)
   or to use `time.perf_counter`, which would make the O(n) rewrite win as the
   docstring promises. This changes what the pack measures, so it is a real
   decision, not a typo fix.
